## 1. 「为什么用最新的 250 版，整合包才 233」

**结论：成立，且已实测可低成本修复。**

### 证据

- `gradle.properties`：`neo_version=21.1.250`；本机 Gradle 缓存中只有 `neoforge-21.1.250-*` 一套产物。
- `maven.neoforged.net` 实际存在的 1.21.1 版本线：… 21.1.231, 21.1.232, **21.1.233**, 21.1.234 … 21.1.250, 21.1.251。kkz 说的 233 确实存在且可用。
- `neoforge.mods.toml` 里 `versionRange = "[21.1,)"` —— 元数据层面允许 233 加载，所以问题不在依赖声明，而在**编译基线**。

### 实机验证（决定性）

把项目完整副本的 `neo_version` 改成 `21.1.233`，用本机 Gradle 8.14 + JDK 21.0.11 执行 `compileJava`：

```
BUILD SUCCESSFUL in 3m 30s
9 个警告（全部是 mixin 的 "Unable to locate obfuscation mapping for @Shadow field"，与 refmap 关闭有关）
```

**结论：源码没有使用 21.1.234~250 之间新增的任何 API，把编译基线降到 233 零改动即可通过。**

### 影响与修复

- 当前发布的 jar 编译基线是 250。虽然 mods.toml 允许 233 加载，但「编译在 250 / 运行在 233」这种组合属于未验证状态，整合包作者无法接受，这是合理的拒绝理由。
- 修复：`neo_version` 改为目标整合包的版本（233），重新构建并重新发布。
- 兼容策略可选其一：单版本对齐 233；或维护 233/250 两条构建线。

## 2. 「环境变量配置有问题，源码只能在你自己的机器上构建」

**结论：成立。** 项目里确实带了本机特有的构建环境耦合。

### 证据清单

| # | 位置 | 问题 |
|---|---|---|
| 1 | `gradle.properties:7` `systemProp.javax.net.ssl.trustStoreType=Windows-ROOT` | Windows 专有 KeyStore 类型。Linux/macOS 上该类型不存在，Gradle JVM 下载依赖时会失败或告警。这是本机 MITM 代理根证书不在 JDK cacerts 里的临时绕过手段，与 mod 功能无关 |
| 2 | 构建日志首行 `Picked up JAVA_TOOL_OPTIONS: -Djavax.net.ssl.trustStoreType=Windows-ROOT` | 说明当初构建还依赖外部注入的环境变量，别人照抄源码也复现不了 |
| 3 | `build.gradle:179` `-Dmixin.env.disableRefMap=true` 写死在 compileJava 的 fork JVM | dev 专用开关硬编码进构建脚本 |
| 4 | `docs/BATCH-PLAN.md:4,50` `F:\DeepSeek\bilibili\NetMusicCanPlayBili-1.21.1` | 文档里硬编码本机绝对路径 |
| 5 | 本机 `PATH` 指向 `C:\Program Files\Java\jdk-21\bin`（不存在），实际 JDK 在 `D:\Java\jdk-21.0.11`，`JAVA_HOME` 未生效 | 本机环境本身不规范，放大了「只有你能构建」的观感 |
| 6 | Gradle wrapper 需要 `services.gradle.org` / `release-assets.githubusercontent.com` | 本次实测 DNS 解析失败，只能改用本机已缓存的 gradle-8.14 发行版才跑通 |

### 修复建议

- 删除 `systemProp.javax.net.ssl.trustStoreType=Windows-ROOT`（需要的话改成本机 `~/.gradle/gradle.properties`，不进仓库）。
- `-Dmixin.env.disableRefMap=true` 改为可选：读取项目属性，缺省不注入。
- 文档中的绝对路径改为相对路径描述。
- README 增补「先决条件」：JDK 21、可访问 `maven.neoforged.net` 与 Modrinth maven、Gradle wrapper 首次需联网。

## 3. 「大量 26 版代码残余，甚至有几个无功效的僵尸快捷键」

**结论：僵尸快捷键成立，且有两条；26.x 残留部分成立，但多为有意保留而非失控。**

### 3.1 僵尸快捷键（实证）

**（a）`clear_equipped_bindings` 是一条完整的死链路**

- 语言键 `key.net_music_can_play_bili.clear_equipped_bindings`（"清理头戴装备绑定"）在 zh_cn 与 en_us 都存在。
- 全项目只注册了 **1 个 KeyMapping**（`HolographicGlassesKeyHandler.OPEN_CONFIG`，H 键）。没有为它注册任何键位。
- 它的服务端实现却存在且完整：`ClearEquippedBindingPacket`（已注册进 `ModernTurntableNetwork`，handle 逻辑齐全，含 4 条 `equipment_bindings.*` 文案）——但 **全项目没有任何一处 `sendToServer(new ClearEquippedBindingPacket())`**，这个包永远不会被发出。
- 也就是说：26.x 时代这个快捷键的功能被删了，但翻译键 + 网络包 + 服务端逻辑都留了下来。这是典型的「无功效的僵尸快捷键」。

**（b）唯一真实快捷键的英文名缺失（反向问题）**

- `key.net_music_can_play_bili.holographic_glasses_config` 只存在于 zh_cn。en_us 里没有这一条。
- 后果：英文客户端里这唯一的快捷键在按键设置中显示为原始键名 `key.net_music_can_play_bili.holographic_glasses_config`。
- 语言文件对齐差异：zh_cn 152 键 vs en_us 146 键，另外 6 条也是仅中文（`video_projector.linked/unlinked`、`mp4.links_unlinked`、`holographic_glasses.mp4_linked_count/mp4_slots_full`、`tooltip.holographic_glasses.mp4_count`）。

### 3.2 26.x 代码残留（实证）

| 项 | 位置 | 性质 |
|---|---|---|
| 孤儿 mixin | `mixin/MinecartRevolutionProjectorLinkCleanupMixin.java` | 不在 `mixins.json` 中，会被编译进 jar 但永不装配。注释说明是有意保留（等第三方 mod 出 1.21.1 版） |
| 死代码块 | `build.gradle:87` `if (false) { ... }` | Bench 契约占位，永不可达 |
| Bench 配置残渣 | `gradle.properties` 的 `enableModBench`、`modbench_version`；`build.gradle` 的 `sharedMediaRunProperties` 22 条 | 移植版不跑 Bench，配置却完整保留 |
| 移植适配层 | `port/shim/` 6 个类 | 有意设计（保持 26.x 调用形态），非残留 |
| 注释 | 57 处源码注释含 26.x 对照说明 | 文档性质，无害但增加噪音 |

### 3.3 顺带核对，这些**不是**问题

- **资源孤儿：未发现。** 24 个模型 / 28 张贴图 / 6 个 blockstates 全部有引用；item 模型走 1.21.1 约定式查找（`models/item/<id>.json`），不需要显式引用。
- **无引用 Java 类：只有 16 个，全部是 mixin**（mixin 靠 `mixins.json` 字符串装配，代码里不出现属正常）。唯一的真孤儿就是上面那条 MinecartRevolution。
- **测试无外部网络依赖：** 941 个用例里没有 @Disabled/assumeTrue，URL 全是 `example.invalid` 之类的假域名；`learningcontainer` 只出现在一个字符串常量断言里，不发起请求；需要真实 HTTP 的用例走本地 `127.0.0.1` 测试服务器。
- **native 资源完整：** 6 平台 × (avcodec/avutil/swscale/jni/许可) 与上游逐文件一致。
